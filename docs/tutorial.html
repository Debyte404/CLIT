CLIT: Learn Git by Building It in C

A beginner-first tutorial for someone who knows basic C, but does not know Git internals yet. We will build the project one tiny idea at a time.

Start Here: You Are Not Supposed To Know This Yet

If words like object database, staging area, tree, ref, or HEAD feel confusing, that is normal. Git hides a lot behind familiar commands. This tutorial does not assume you know Git internals. It starts from plain files and folders, then slowly builds toward the real model.

How to use this tutorial: For every concept, read the eight small boxes in order. Then write only the code for that milestone. Do not jump ahead. The point is to understand enough to explain it in an interview.
Your current levelBasic C syntax, structs, linked lists, queues, and simple programs.
What we will addFiles, folders, byte buffers, hashes, compression, parsing, and command design.
What we will avoid todayMerges, remotes, packfiles, rebase, and Git's full binary index format.

The Whole Project In One Picture

CLIT is a program that takes snapshots of your project. A snapshot means: "these exact file contents existed at this time." Git stores those snapshots using small objects that point to each other.

file contentbytes in README.md
->
blobstores file bytes
->
indexstaging list
->
treedirectory snapshot
->
commitnamed snapshot
->
branchlatest commit

Git Words From Zero

Concept: Repository

1. What is it?A normal project folder plus a hidden database folder.
2. Commandclit init
3. Files.clit/, .clit/objects, .clit/refs, .clit/HEAD
4. C neededmkdir, fopen, fprintf, return codes.
5. Code shapeA cmd_init function creates folders and writes HEAD.
6. Why it worksCLIT needs one private place to store history separately from your files.
7. TestRun Get-ChildItem -Recurse .clit.
8. LearnedVersion control starts as filesystem organization.

Concept: Commit

1. What is it?A saved snapshot with a message and parent pointer.
2. Commandclit commit -m "message"
3. FilesCommit object in .clit/objects, branch file in .clit/refs/heads/main.
4. C neededString formatting, timestamps, file reads and writes.
5. Code shapeCreate text payload, store as object, update branch ref.
6. Why it worksA commit remembers which tree was the project state.
7. TestPrint it with clit cat-file -p <hash>.
8. LearnedHistory is a chain of commit objects.

Concept: Staging Area

1. What is it?A list of files you want in the next commit.
2. Commandclit add README.md
3. Files.clit/index
4. C neededStruct arrays, string comparison, updating a text file.
5. Code shapeStore path, mode, and blob hash for each staged file.
6. Why it worksYou choose the next snapshot before making the commit.
7. TestOpen .clit/index and read the staged entries.
8. Learnedadd does not commit. It prepares.

Concept: Hash

1. What is it?A fixed-length name calculated from content bytes.
2. Commandclit hash-object README.md
3. Filessrc/sha1.c, src/object.c
4. C neededByte buffers, OpenSSL SHA-1, hex conversion.
5. Code shapeRead bytes, add header, hash the complete buffer.
6. Why it worksSame content gives the same hash. Different content gives a different hash.
7. TestRun twice on the same file and compare output.
8. LearnedGit names data by what it contains.

Concept: HEAD and Branch

1. What is it?HEAD tells CLIT which branch is current.
2. Commandtype .clit\HEAD
3. Files.clit/HEAD, .clit/refs/heads/main
4. C neededRead a small text file, trim newline, build a path.
5. Code shapeResolve ref: refs/heads/main into a real file path.
6. Why it worksA branch is just a pointer to the latest commit.
7. TestAfter commit, branch file should contain a commit hash.
8. LearnedBranches are lightweight because they are tiny files.

The Build Milestones

Milestone 1: Make clit init Real

1. What are we making?A command that turns a normal folder into a CLIT repository.
2. What command proves it?bin\clit init
3. What files are involved?src/main.c, src/repo.c, include/clit.h, and the new .clit folder.
4. What C do we need?argc, argv, strcmp, mkdir, fopen, and checking return values.
5. What code shape?main checks the command name. cmd_init creates each folder once and writes HEAD.
6. Why does it work?All future commands need a private database folder. init creates that database.
7. How do we test it?Delete old .clit, run init, list folders, read HEAD.
8. What did we learn?A repository is just a normal folder plus structured metadata.

Sub-concept: command dispatch

main should behave like a traffic controller. It does not do the work itself. It reads argv[1] and calls the right command.

if (argc < 2) {
    printf("usage: clit <command> [args]\n");
    return 1;
}

if (strcmp(argv[1], "init") == 0) {
    return cmd_init(argc - 1, argv + 1);
}

Sub-concept: repository layout

.clit/ HEAD says which branch is current objects/ stores compressed blobs, trees, commits refs/ heads/ main will store latest commit hash later
make
bin\clit init
Get-ChildItem -Recurse .clit
Get-Content .clit\HEAD

Milestone 2: Store File Content with hash-object

1. What are we making?A command that turns one file into a stored object.
2. What command proves it?bin\clit hash-object -w README.md
3. What files are involved?src/object.c, src/sha1.c, include/utils.h, .clit/objects.
4. What C do we need?Read whole files, allocate buffers, hash bytes, compress bytes, write binary files.
5. What code shape?read_file, make_object_buffer, sha1_hex, write_object.
6. Why does it work?The object name is based on the bytes, so CLIT can find identical content by hash.
7. How do we test it?Run twice. Same file should print the same hash.
8. What did we learn?Git stores content first, filenames later.

Sub-concept: object header

Git does not hash only the file bytes. It hashes a header plus the bytes. For a text file with 12 bytes, the object starts like this:

blob 12\0hello world

The \0 is a NUL byte, not the characters backslash and zero. This is why we need byte buffers, not just strings.

Sub-concept: object path

If the hash is abcdef..., store it as:

.clit/objects/ab/cdef...

Milestone 3: Read Objects Back with cat-file

1. What are we making?A command that proves stored objects can be read and understood.
2. What command proves it?bin\clit cat-file -p <hash>
3. What files are involved?src/object.c and the compressed file under .clit/objects.
4. What C do we need?Path building, binary file reads, decompression, parsing bytes.
5. What code shape?read_object(hash) returns type, size, and payload.
6. Why does it work?The header tells CLIT what kind of object it loaded.
7. How do we test it?-t prints blob, -p prints original content.
8. What did we learn?Storing data is only half the job. Parsing proves the format.

Sub-concept: parsing the header

blob 12\0hello world
^^^^ ^^  ^^^^^^^^^^^
type size payload

Milestone 4: Stage Files with add and status

1. What are we making?A staging list for the next snapshot.
2. What command proves it?bin\clit add README.md then bin\clit status
3. What files are involved?src/index.c, src/object.c, .clit/index.
4. What C do we need?Structs, arrays, string comparison, reading and rewriting text files.
5. What code shape?An IndexEntry struct with path, mode, and hash.
6. Why does it work?The index says what should go into the next commit.
7. How do we test it?Read .clit/index after adding a file.
8. What did we learn?Staging is a deliberate preparation step.

Sub-concept: simple index format

100644 <blob-hash> README.md
100644 <blob-hash> src/main.c

This is not Git's real binary index. That is okay. We are learning the model first.

Milestone 5: Create Directory Snapshots with write-tree

1. What are we making?A tree object that represents staged files as a snapshot.
2. What command proves it?bin\clit write-tree
3. What files are involved?src/tree.c, .clit/index, .clit/objects.
4. What C do we need?Read entries, sort them, format tree payload, store object.
5. What code shape?cmd_write_tree loads index entries and writes a tree object.
6. Why does it work?A tree connects filenames to blob hashes.
7. How do we test it?Print the tree with cat-file -p.
8. What did we learn?A project snapshot is a directory object pointing to file objects.

Sub-concept: flat tree first

To keep the first version understandable, start with a flat tree. Recursive folders can come after the simple version works.

Milestone 6: Save History with commit

1. What are we making?A commit object that names a snapshot and links to previous history.
2. What command proves it?bin\clit commit -m "first commit"
3. What files are involved?src/commit.c, .clit/HEAD, .clit/refs/heads/main.
4. What C do we need?String building, timestamps, ref resolution, object writing.
5. What code shape?Write tree, build commit payload, store commit object, update branch file.
6. Why does it work?The branch file moves forward to the newest commit hash.
7. How do we test it?Read .clit/refs/heads/main and inspect the commit object.
8. What did we learn?A commit is a small text object that points to a full snapshot.

Sub-concept: commit payload

tree <tree-hash>
parent <parent-commit-hash>
author Your Name <you@example.com> <timestamp>

message here

Milestone 7: Print History with log

1. What are we making?A command that walks commit history backward.
2. What command proves it?bin\clit log
3. What files are involved?src/commit.c, branch ref, commit objects.
4. What C do we need?Loops, parsing lines, copying hash strings safely.
5. What code shape?Start at current commit, print, replace current hash with parent hash.
6. Why does it work?Each commit knows its parent, so history is a chain.
7. How do we test it?Make two commits and confirm newest appears first.
8. What did we learn?Git history is pointer traversal.

Milestone 8: Restore Files with Basic checkout

1. What are we making?A safe restore command for a chosen commit.
2. What command proves it?bin\clit checkout <commit-hash>
3. What files are involved?src/checkout.c, commit object, tree object, blob objects.
4. What C do we need?Object parsing, writing files, safety checks before overwriting.
5. What code shape?Resolve commit, load tree, load each blob, write files.
6. Why does it work?The commit points to a tree, and the tree points to every blob.
7. How do we test it?Change a file, checkout an older commit, inspect the file.
8. What did we learn?Checkout rebuilds files from stored objects.
Beginner safety rule: Your first checkout should refuse to overwrite changed files. A safe partial implementation is better than a dangerous complete-looking one.

One-Day Build Order

  1. Fix main.c command dispatch and cmd_init.
  2. Write byte-buffer helpers before object code.
  3. Implement hash-object without -w, then add storing.
  4. Implement cat-file so stored objects are inspectable.
  5. Build a simple text index for add and status.
  6. Build flat write-tree.
  7. Build commit and update refs/heads/main.
  8. Build log.
  9. Build conservative checkout.

Manual Verification Path

Every time you finish a milestone, run a tiny proof. If you cannot prove it from the terminal, do not move on yet.

make
bin\clit init
bin\clit hash-object -w README.md
bin\clit cat-file -p <hash-from-previous-step>
bin\clit add README.md
bin\clit status
bin\clit write-tree
bin\clit commit -m "first commit"
bin\clit log

Debugging For Beginners

When a command crashes: Print the values of argc, argv[1], and the path you are opening.
When a file is missing: Check whether the program is running from the repository root.
When hashes differ: Check the exact header and file size. One byte changes the hash.
When parsing is confusing: Print one line at a time and label what you think each part means.

How To Talk About This On A Resume

Built a Git-like version control system in C with repository initialization, content-addressed object storage, compressed blob objects, a staging index, tree snapshots, commit objects, history traversal, and basic checkout.

In interviews, be honest about simplifications. Say that the first version uses a learning-friendly index format, starts with simple tree handling, and does not implement remotes or merges yet.
